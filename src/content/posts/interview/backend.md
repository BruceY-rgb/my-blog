### 1. 如何创建线程池？线程池常见参数有哪些？

创建线程池可以通过JavaScript的`ThreadPoolExecutor`构造函数或者`Executors`工具类实现。核心参数包括

- 核心线程数(维持常驻线程)
- 最大线程数(扩容上限)
- 存活时间(非核心线程空闲时长)
- 任务队列(存放待执行任务)
- 拒绝策略(队列满时的处理方式)

#### 1. 线程池的创建方式

`Java`中线程池的创建主要有两种方式：通过`Executors`工厂类快速创建和通过`ThreadPoolExecutor`手动配置。

在生产环境中使用手动配置可以实现精细化控制

1. 通过`Executors`工厂类创建(快速实现)
   - 固定大小线程池：适用于负载稳定的场景(比如`API`请求)
   - 可缓存线程池：适用于大量段生命周期任务(比如批量数据处理)
   - 单线程池线程池：保证任务顺序执行(如事务处理)
   - 定时/周期性线程池：用于延迟或周期性任务调度(如心跳检测)
2. 通过`ThreadPoolExecutor`手动配置(推荐生产环境)：直接配置核心参数，灵活控制线程池行为


### 2. HashMap底层原理和扩容机制

`HashMap`底层采用 **数组+链表/红黑树结构**，通过哈希算法确认元素存储位置，，默认初始容量为`16`，负载因子为`0.75`。当元素数量超过 *容量 × 负载因子*时触发扩容

扩容时创建**双倍容量**新数组，通过高位运算重新计算节点位置(后来优化为不需要重新`hash`)，元数据通过尾插法迁移到新数组

链表长度超过`8`切数组长度≥`64`时转换为红黑树，提升查询效率

### 3. JVM大的垃圾回收算法

`JVM`主要垃圾回收算法包括：

- *标记清除*：
  - 原理：分标记(遍历图对象)和清除(回收未标记对象)两个阶段
  - 优点：实现简单
  - 缺点：内存碎片化
  - 适用老年代
- *复制算法*：
  - 原理：将堆分为两块，存货对象复制到另一块之后清空原区域
  - 优点：无碎片，效率高
  - 缺点：内存利用率低(仅用`50%`)
  - 适用新生代
- *标记整理*
  - 原理：标记后整理存货对象至内存另一端，清理边界外空间
  - 优点：避免碎片，内存利用率高
  - 缺点：整理耗时，容易造成`STW`(全局停顿)
  - 适用老年代
- *分代收集*
  - 原理：按照对象生命周期划分新生代(复制算法)和老年代
  - 优点：针对性优化效率
  - 缺点：需要协调多代策略
  - 通用方案

> 新生代放刚创建、存活时间短的对象
> 老年代放存活很久、反复使用的对象

### 4. 详细说说Redis的数据类型

1. `String`:存储文本、数字或者二进制数据
2. `List`:双向链表，支持队列和栈操作
3. `Hash`:字段-值映射，适合存储对象
4. `Set`:无序唯一集合，支持并交差运算
    - 应用场景
      - 标签系统
      - 共同好友/关注列表(交集运算) 
5. `Sorted Set`:按分数（元素的一个关联score，元素唯一但是分数可以重复）排序的有序集合
    - 应用场景
      - 排行榜(游记积分榜)
      - 延时队列(用时间戳作为score)
6. `Bitmap`：通过位操作高效存储布尔类型数据，基于`String`实现
    - 应用场景
      - 用户签到记录
      - 实时统计活跃用户
7. `HyperLogLog`:概率型数据结构，用于估算大规模数据的唯一元素数量(误差约为`0.81%`)
    - 应用场景
      - 统计独立访客
      - 大数据去重计数(节省内存)
8. `Geospatial`(地理位置)：存储经纬度信息，支持距离计算、范围查询
   - 应用场景
     - 附近商家推荐
     - 轨迹追踪
9. `Stream`：支持多消费者组的消息队列
    - 应用场景
      - 异步任务队列
      - 事件溯源

### 5. 说说`Redis`的持久化策略

`Redis`提供两种持久化策略：`RDB`和`AOF`

- `RDB`通过定时生成数据快照实现，适合快速恢复但是可能丢失部分数据
- `AOF`记录所有写操作命令，数据完整性更高但是文件较大

Redis支持混合持久化模式（AOF+RDB），结合两者优势实现高效备份与恢复。

### 8. TCP协议如何保证可靠传输

1. 序号+累计ACK+超时重传保证数据不漏、不乱
2. 校验和保证 **数据不损坏**
3. 滑动窗口与流量控制保证 **发送速率可控**
4. 拥塞控制保证 **网络不被压垮**
5. `SACK`/时间戳等选项进一步 **优化效率与准确性**

> - `SACK`:选择`ACK`，接收方告知发送方除了首个缺失外，后续哪些分段已收到，发送方仅重传真正丢失的部分
> - 时间戳：用于更准确地估算`RTT`并抑制旧报文

### 9. Redis中的`Zset`怎么实现的

`Redis`的`Zset`通过跳跃表和哈希表实现，既支持快速的范围查询，又保证元素的唯一性和有序性

哈希表存储成员到分数的映射以支持快速查询，跳跃表按照分数排序成员以支持高效的范围操作

两者结合确保插入、删除和查询的时间复杂度为 $O(logn)$。数据量小时可能使用压缩列表优化内存

### 10. 消息队列如何保证消息不丢

消息队列通过多环节保障机制防止消息丢失：
- 生产者使用确认机制(如`ACK`)确保消息成功发送至`Broker`;`Broker`采用持久化存储(如磁盘写入)和副本同步防止数据丢失
  - `Broker`:消息队列服务端
- 消费者处理成功后手动提交确认，失败时触发重试
- 消息重试机制和死信队列异常情况
- 整体通过事务机制或幂等设计保证端到端一致性

### 11. 什么是进程和线程？进程和线程的区别

进程是操作系统中资源分配的基本单位，线程是进程中执行的基本单位，进程拥有独立的内存空间，而线程共享进程的内存空间和资源

#### 1. 进程

- 定义：进程是一个正在执行的程序实例，是 **操作系统进行资源分配和调度的基本单位**
- 特点：
  - **独立性**：每个进程都有自己的内存空间(代码段、数据段、堆、栈)
  - **资源拥有**：进程拥有自己的文件描述符、信号处理、地址空间等资源
  - **开销较大**：进程切换需要保存和恢复大量上下文信息

#### 2. 线程

- 定义：线程是进程中的一个执行路径，是**CPU调度和执行的基本单位**
- 特点
  - **共享性**：同一进程的线程共享进程的内存空间和资源
  - **轻量级**：线程切换开销小，创建和销毁速度快
  - **并发执行**：多个线程可以在多核`CPU`上**并发执行**，提高程序效率

线程衣服御锦城，共享进程的资源，但是也拥有私有资源

- 私有栈
- 寄存器
- 程序计数器

#### 3. 进程与线程的应用场景

- 进程：适用于需要高隔离性和稳定性的场景，如服务器进程、独立应用程序
- 线程：适用于需要高并发和快速响应的场景，如多线程服务器、实时应用

### 13. 如何监控并优化慢`SQL`

### 14. 数据库中的数据被误删了怎么恢复

#### 1. 区分删除类型
- DELETE：仅删行，可通过日志 / 闪回恢复
- TRUNCATE：清空表，依赖备份恢复
- DROP：删除表 / 库，基本只能靠备份

#### 2. 恢复优先级

- 未提交事务：执行 `ROLLBACK` 直接回滚
- 已提交、开启日志：利用日志做时间点恢复
- 有备份：全量备份 + 增量日志，还原至删除前
- 无备份无日志：尝试应用日志、缓存，成功率低

#### 3. 主流库简要方案

- `MySQL`：通过 binlog 解析，反向补回数据
- `Oracle`：使用闪回查询 / 闪回表快速恢复
- `SQL Server/PostgreSQL`：依靠备份 + 事务日志 / WAL 做时间点还原
- 云数据库：控制台直接使用时间点回溯


### 15. 事务是什么？有什么特性？事务的隔离性是什么

事务就是：把一组数据库操作打包成一个整体，要么全部成功，要么全部失败，不会执行一半

<aside class="admonition example">
去银行转账：

1. 银行扣你的钱
2. 银行的账户价钱

事务必须保证：**要么两步都成功，要么都撤销**
</aside>
#### 四大特性`ACID`

- 原子性：不可分割，要么全做，要么全部做
- 一致性：操作前后数据整体不变(转账前后总金额一样)
- 隔离性：多个事务同时跑，互不干扰
- 持久性：一旦提交成功，数据永久保存，断电也不会丢失

#### 事务隔离性

- 三种并发问题
  - 脏读：读到其他事务未提交的数据(会回滚，数据无效)
  - 不可重复读：同一事务内，**两次查询结果不一样**
  - 幻读：同一事务内，**查询到新增/消失的行**
    - 别的事务插入/删除了数据
    - InnoDB 在可重复读级别下，用 间隙锁（Gap Lock）直接解决幻读 → 不让别人在你查询的范围内插入数据。
- 四种隔离级别
  - 读未提交：最低，会脏读
  - 读已提交：防止脏读，允许不可重复读
  - 可重复读：防止脏读+不可重复读
  - 串行化：最高，全防，但是性能最慢


### 16. 什么是心跳机制？

心跳机制是长连接中用于检测连接是否存活的机制，客户端和服务端定期互发轻量级 ping/pong 消息，超时未响应则判定连接异常并触发清理或重连。

#### 解决什么问题

- **半开连接**：用户断网、浏览器休眠、NAT 超时后，服务端无法立即感知连接已失效
- **资源浪费**：无效连接持续占用 socket、内存等资源
- **在线状态不准**：异常断线无法及时反映到在线状态

#### 实现方式

- 连接建立后，每隔 N 秒发送 ping
- 收到 pong，更新 `lastActiveTime`
- 连续多次超时未收到 pong → 判定失效
- 关闭连接、释放资源、触发重连或下线逻辑

#### 心跳间隔设置

- 一般 **20~30 秒**一次心跳，超时时间 = 2~3 个心跳周期
- 实时性要求高（IM 聊天）→ 适当缩短；后台连接 → 可放宽

#### 项目实战（聊天系统）

- WebSocket 连接通过 Socket.IO 的 ping/pong 检测存活
- 心跳失败触发自动重连 → 重新 `join` channel room / dm room / user room（**业务恢复**）
- 在线状态：Redis 存 `presence:userId = online`，设 TTL，每次心跳刷新 TTL；TTL 到期自动过期实现离线

### 17. 滑动窗口是什么？

滑动窗口在面试中有两种语境：**限流算法**和 **TCP 流量控制**，需先确认面试官问的是哪种。

#### 限流中的滑动窗口

**定义**：统计当前时间往前推一个窗口范围内的请求数量，判断是否超过阈值。

**对比固定窗口**：

| 方式       | 统计逻辑                         | 问题                         |
| ---------- | -------------------------------- | ---------------------------- |
| 固定窗口   | 按整分钟/整秒统计（12:00~12:01） | 边界突刺：边界处短时间可翻倍 |
| 滑动窗口   | 当前时间往前推 N 秒平滑滑动      | 避免边界突刺，限流更平滑     |

> 例：限制每分钟 100 次。固定窗口下，12:00:59 发 100 次 + 12:01:00 发 100 次，1 秒内 200 次被判合法，这就是边界突刺。

**Redis 实现**（Sorted Set）：

1. `ZREMRANGEBYSCORE key 0 now-window` — 删除窗口外旧记录
2. `ZCARD key` — 统计当前窗口内请求数
3. 超过阈值 → 拒绝；否则 `ZADD key now requestId` 写入当前请求
4. `EXPIRE key window` — 设置过期时间

**项目应用**：发消息限流、验证码发送限流、登录失败限流、附件上传限流等，防止刷接口或恶意请求。

#### TCP 中的滑动窗口

**定义**：TCP 用于**流量控制**和**提高传输效率**的机制。发送方在窗口范围内连续发送多个包，不必每个包都等 ACK。接收方通过通告窗口告知自己还能接收多少数据，发送方据此控制发送速率。

**解决什么问题**：

- 提高吞吐量：允许批量发送，不等每个 ACK
- 流量控制：防止发送方速率超过接收方处理能力（≠ 拥塞控制，拥塞控制关注的是网络链路是否拥塞）

**工作方式**：

1. 发送方维护发送窗口，窗口内数据可连续发送
2. 收到 ACK 后窗口向后滑动，允许发送后续数据
3. 接收方动态调整通告窗口大小，控制发送速率

> 流量控制关注**接收方**处理能力，拥塞控制关注**网络链路**是否拥塞，两者不同。
