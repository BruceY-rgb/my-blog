## 1. 项目介绍

这是一个面向银行客户经理和信贷检查场景的只能授信材料分析与报告生成平台。它解决的问题是：企业授信调查和贷后检查过程汇总，大量信息分散在营业执照、财报、征信、合同、抵押物资料和访谈记录中，人工收集慢、重复录入多、字段容易错漏

我负责`Agent SDK`服务层的架构设计和核心业务封装：把文档解析、信息检索、结构化抽取、字段校验、交互式复核、模板填充和Word报告生成封装成可组合的`Agent`工具

核心技术上，我使用了`Prompt Engineering`，`LangChain/RAG`和`Anthropic`模型做结构化信息抽取，并设计了文件索引树、字段树和交互式复核机制，解决了表单字段多、来源复杂、模型容易幻觉和字段冲突的问题

## 2. 简历中提到的内容解答

### 2.1 Agent SDK服务层架构设计、接口定义、业务逻辑封装

我负责把大模型能力从单次`API`调用封装成可以被业务系统稳定使用的`Agent`服务层。

具体来说，我设计了`Agent Query`、文件上传、报告生成、字段抽取、模板渲染等接口，把文档解析、索引检索、结构化抽取、字段校验和报告生成封装成可以组合的业务工具。前端只需要提交任务、文件和用户意图，服务层负责模型配置、工具权限、prompt组装、流失响应、错误处理和业务规则执行

**核心流程**

- 系统解析输入材料，构建文件索引树和字段树
- 需要填写某个字段的时候，服务层现根据字段路径检索相关`evidence chunks`
- 通过`Agent SDK`把字段定义、候选证据和输出`schema`发给`Claude`，让它生成结构化结果
- 后端做格式校验、置信度判断和人工复核

```
用户 / 客户经理
      ↓
前端 UI：上传材料、发起任务、确认字段
      ↓
Agent Service：任务状态、权限、审计、workflow
      ↓
Claude Agent SDK：agent loop、上下文、工具调用、streaming
      ↓
Claude：理解、推理、抽取、生成
      ↓
业务工具：RAG 检索、文件索引树、字段树、报告模板、校验器
      ↓
结果：结构化字段 + evidenceRefs + Word 报告 + 待复核项
```

!!! note Claude Agent SDK
它提供的是一套通用`Agent`的运行标准。不是普通的模型API（一问一答），而是把`Claude Code`里的agent loop、工具调用、上下文管理、流式交互和权限控制开放给开发者。开发者可以把自己的文件系统、数据库、检索服务、OCR服务、报告生成服务封装成工具，让`Claude`在受控范围内调用这些工具完成多步任务

claude code封装好了一些比较复杂的能力：

```
模型调用
多轮 Agent loop
工具调用
流式输出
上下文管理
MCP 工具生态
权限控制
错误处理
session 管理
```

我们只是在外面加了一层

```
自己的 UI
自己的账号系统
自己的文件系统
自己的业务工具
自己的 prompt
自己的数据库
自己的工作流
```
</aside>
1. 为什么要有服务层  
   不能让前端直接调模型，因为模型供应商、prompt、工具权限、工作目录、错误重试、日志审计都应该由后端统一控制。

2. 服务层封装了什么  
   - Agent 会话接口  
   - 文件管理接口  
   - 报告生成接口  
   - 字段抽取工具  
   - 模板渲染工具  
   - 模型配置和工具白名单  
   - 流式响应和异常处理

3. 接口设计思路  
   对外保持稳定 API，对内可以替换 Anthropic、Bedrock、Vertex AI 或其他模型。业务代码不直接依赖某一个模型 SDK。

4. 业务逻辑封装思路  
   Agent 不直接“自由操作系统”，而是通过高层业务工具完成动作，例如 `get_field_evidence`、`generate_report`、`validate_report_completeness`。这样更可控，也更方便审计。

常见追问：

Q：你说主导服务层，具体主导了什么？

> 我主导的是服务层边界和核心接口设计，包括前端请求如何进入 Agent 服务、Agent 可以调用哪些业务工具、工具输入输出 schema 怎么定义、模型流式结果怎么返回、异常和超时怎么处理，以及文件和报告生成服务如何解耦。我的重点不是写一个 prompt，而是让模型能力以稳定服务的方式接入银行业务流程。

Q：Agent SDK 在这里起什么作用？

> Agent SDK 负责把模型推理和工具调用结合起来。它不是单纯文本生成，而是可以在受控工具集合内完成读取材料、检索证据、抽取字段、生成报告等动作。服务层的作用是给 Agent SDK 加上业务边界、权限边界和工程化能力。

避坑说法：

- 不要说“我就是调了 Claude API”。  
  要说“我把模型调用封装成服务层，并设计了工具、权限、接口和业务流程”。

- 不要说“Agent 可以随便读写文件”。  
  要说“Agent 只能调用白名单业务工具，并且受任务目录和权限控制约束”。

### 2.2 Prompt Engineering + LangChain 优化 Anthropic 模型，准确率 98%

简历原意：

> 利用 Prompt Engineering 和 LangChain 优化 Anthropic 模型，将自动化信息提取的准确率提升至 98%，并成功部署于新加坡某领先银行。

这一部分主要是优化企业授信材料的**结构优化信息抽取效果**

单纯把所有材料丢给大模型会导致上下文噪音大、字段混淆、格式不稳定和模型脑补等问题。

我通过`Prompt Engineering`明确角色、字段`schema`、缺失值规则、来源优先级、单位格式和禁止猜测原则

通过`LainChain`编排文档加载、`chunk`切分、检索、`prompt template`、`output parser`和重试流程。

最终在核心字段集合上做字段级别评测，准确率提升到约98%

可以展开的技术点：

1. Prompt Engineering 优化了什么
    - 角色：银行授信分析师
    - 任务：只做字段抽取和证据归因，不自由发挥
    - 输出：固定`JSON/schema`
    - 缺失值：没有证据就输出 **未提供/无法确认**
    - 格式：日期、金额、百分比、是否统一规范
    - 冲突：保留候选值和来源，不让模型擅自决定

2. `LangChain`做了什么
    - `Document Loader`：接入`PDF`、`Word`、`Excel`、`OCR`文本
    - `Text Splitter`：按页码、章节、表格和业务语义切分`chunk`
    - `Retriver`：关键词+向量+业务索引混合检索
    - `Prompt Template`:不同字段和材料类型使用不同模板
    - `Outpu Parser`:解析结构化输出并做校验
    - `Retry`:解析失败字段或字段缺失时触发重试

3. Anthropic 模型为什么适合  
   Claude 对长上下文、复杂指令遵循、结构化输出和文档理解表现比较稳定，适合授信材料这种长文档、多字段、低容错场景。

4. 98% 怎么解释  
   按字段级准确率评估，不是整篇报告完全一致。先准备人工标注样本，把模型输出字段和标准答案做归一化比对，例如金额统一单位、日期统一格式、百分比统一精度。核心字段正确率约 98%。


常见追问：

Q：98% 是怎么算出来的？

> 我们按字段级准确率算。每份材料对应一组人工标注的标准字段，模型输出后先做归一化，比如金额单位、日期格式、公司名称空格和全半角，再和标准答案比对。材料里确实没有的字段，如果模型输出“未提供”，也算正确。这个 98% 指核心字段集合上的自动抽取准确率。

Q：Prompt 怎么调优的？

> 我不是只改一句提示词，而是按问题分类调。字段名漂移就用固定 schema；金额日期格式不稳定就加格式约束和示例；模型脑补就明确无证据返回未提供；多来源冲突就要求返回候选值和 needs_review；JSON 解析失败就用 output parser 和重试机制。

Q：LangChain 的价值是什么？

> LangChain 主要解决工程编排问题，不是智能来源。它把文档加载、切分、检索、prompt、模型调用、输出解析和重试串成稳定链路，让抽取流程可复用、可监控、可评估。

Q:LangChain和Claude Agent SDK会不会冲突

> 不会，因为它们关注的层级不同。`Claude Agent SDK`更偏向执行层，负责`Claude`的多轮`agent loop`、工具调用、上下文管理和流式交互；`LangChain`更偏向`LLM`应用编排层，负责文档加载、文本切分、`RAG`检索、Prompt Template、Output Parser 和重试链路
>
> 在我们项目里，我会让 Claude Agent SDK 做外层主调度器，负责理解用户任务并调用高层业务工具；LangChain 放在工具内部，负责具体的字段检索和结构化抽取。例如 Agent 调用 get_field_evidence，这个工具内部会用 LangChain 从文件索引树和向量库里召回相关 chunk，再组装 prompt 调 Claude 输出结构化 JSON。
>
> 真正需要避免的是职责重叠：不要同时用 Claude Agent SDK 和 LangChain Agent 都做主规划，也不要重复管理工具和上下文。我们会让业务数据库作为唯一状态源，Agent SDK 管会话和工具调度，LangChain 管 RAG 子链路，这样二者是互补关系。

### 2.3 树状索引、交互式填写、熔断降级与负载均衡

简历原意：

> 针对智能 Agent 表单填写不准确问题，设计创新的“树状索引”信息检索机制和“交互式填写”流程，结合熔断、降级、负载均衡策略，提升系统稳定性和数据准确性。

建议把“树状索引”升级表达为“文件索引树 + 字段树”：

> 这里的树状索引不是普通目录树，而是两套结构：文件索引树回答“证据在哪里”，字段树回答“报告需要什么字段”。系统通过 evidenceRefs 把字段和证据连接起来。

表单填写不准确的根因是字段多、来源分散、相似字段多、模型容易在无关上下文中混淆。所以我设计了文件索引树和字段树

- 文件索引树按照任务、业务分类、文档、`chunk`组织材料
- 字段树按报告章节和字段规则组织目标表单

填写某个字段的时候，系统不是让模型读全部文件，而是**按照字段路径和业务分类检索最相关`chunk`**，再做结构化抽取和校验

对低置信度、冲突或者高风险字段，进入交互式复核。

稳定性上，模型调用层做了超时、重试、熔断和负载均衡，**避免模型波动影响主流程**

1. 文件索引树  
   - 任务根节点：一次授信分析任务  
   - 业务分类节点：企业主体、财务、担保、征信、经营  
   - 文档节点：营业执照、财报、征信报告、合同  
   - chunk 节点：页码、表格、bbox、时间段、文本、字段候选

2. 字段树  
   - 报告章节  
   - 字段名  
   - 字段别名  
   - 数据类型  
   - 推荐来源  
   - 校验规则  
   - 置信度阈值

3. 交互式复核  
   - 低置信度字段让用户确认  
   - 多来源冲突展示候选值和来源  
   - 高风险字段强制人工确认  
   - 用户修订结果进入审计记录

4. 稳定性策略  
   - 熔断：错误率、超时率、P95 延迟异常时暂停调用主模型  
   - 降级：切轻量模型、规则抽取、缓存结果或人工补录  
   - 负载均衡：多 endpoint、多供应商、多模型按延迟、配额、错误率路由

常见追问：

Q：树状索引和普通向量检索有什么区别？

> 普通向量检索是扁平 chunk 召回，适合问答，但不够理解业务结构。文件索引树会先按任务、业务分类、文档和 chunk 组织材料；字段树会记录字段定义、别名、来源优先级和校验规则。检索时先按业务域缩小范围，再做关键词和向量召回，最后绑定 evidenceRefs。所以它是在向量检索上增加业务结构、证据追溯和字段校验能力。

Q：交互式填写怎么提升准确率？

> 它不是让用户重新手工填，而是只处理模型不确定的部分。比如注册资本有两个候选值，系统会展示候选值、来源文件、页码、chunk 和置信度，让用户确认。高置信度字段自动填，低置信度或冲突字段人工确认，这样在效率和准确性之间取得平衡。

Q：熔断、降级、负载均衡在 LLM 场景怎么落地？

> 我会把模型当作高延迟、高成本、可能波动的外部依赖。调用层记录错误率、超时率、限流错误和延迟指标，超过阈值就触发熔断；主模型不可用时降级到备用模型、规则抽取、缓存或人工补录；多 endpoint 之间根据延迟、配额和错误率做路由。


## 3. 介绍项目

> 这个项目是企业级智能授信材料分析与报告生成平台，主要服务信贷客户经理和贷后检查团队。业务上，银行在做企业授信、贷后检查或者客户尽调时，需要从营业执照、财务报表、征信报告、合同、抵押物材料、访谈录音等大量异构材料中提取信息，再填入标准表单和检查报告。传统做法非常依赖人工，效率低，而且容易出现字段漏填、单位错误、信息来源不一致和证据难追溯的问题。

我主要负责 Agent SDK 服务层设计和核心 workflow 封装，把真实内容解析、文件索引树构建、结构化抽取、字段校验、多来源融合、交互式复核和模板生成拆成可组合的服务。模型侧主要基于 Anthropic Claude，结合 Prompt Engineering 和 LangChain 做文档检索增强与结构化输出。为了提高复杂表单填写准确率，我设计了“文件索引树 + 字段树”的机制：文件索引树把材料组织成业务语义和 chunk 级证据，字段树把报告模板拆成明确字段和校验规则。系统填写字段时不是全量丢给模型，而是按业务分类和字段路径检索最相关证据，再做结构化抽取和校验。

对于低置信度、冲突字段或高风险字段，系统进入交互式复核流程，让用户确认或补充，从而提升准确率和可审计性。工程化上，服务层还设计了模型调用的熔断、降级和负载均衡策略，避免单个模型接口超时或限流影响整体流程。最终目标不是简单生成一段文本，而是稳定生成可复核、可追溯、可编辑的银行业务报告。

## 4. 系统架构

![整个项目架构](/my-blog/2026/05/25/interview/creditagent/image-2.png)

**服务层的workflow**

1. 接入层
    负责用户上传文件、任务创建、文件元数据记录和权限控制。主要包括批量上传、任务ID生成、文件存储、命名规范、用户身份和访问控制

2. 解析层
   负责所有文件的真是内容解析，而不是只看扩展名或文件名。图片走`OCR/VLM`，`PDF`区分文本型和扫描型，`Excel`做`sheet`、表头、合并单元格和财务结构解析，音频做`ASR`转写、说话人去人和摘要提取 


!!! note "ASR"技术

ASR 是 Automatic Speech Recognition，自动语音识别，简单说就是：把一段音频自动转换成文字。

```
音频输入
  ↓
声音预处理
  ↓
声学特征提取
  ↓
语音识别模型
  ↓
语言解码
  ↓
输出文字
```
</aside>
3. 索引层
    构建统一的文本索引树和`chunk`级只是单元把材料按照企业主体、财务状况、担保抵押、征信司法、经营情况等业务语义组织起来，并挂接来源页、证据片段、字段候选和置信度。

4. 认知层  
   负责业务语义理解和多来源信息融合，包括企业主体信息抽取、财务指标抽取、担保和抵押信息抽取、风险点识别、字段冲突对齐和置信度评分。

5. 生成层  
   负责报告章节规划、结构化字段填充、证据引用、Word/PDF 导出和结果可编辑化。正式报告不是让模型自由生成整篇文章，而是先确定字段和证据，再组织成报告章节。

6. 交互层  
   负责 Agent 和人工协同，包括证据追溯问答、字段修订、章节重生成、风险解释和报告完整性校验。

## 5. Agent SDK服务层原理

面试官可能会问：“Agent SDK 服务层到底做了什么？为什么不是前端直接调模型？”

回答：

> Agent SDK 服务层的核心价值是隔离模型能力和业务系统。前端不应该直接知道模型供应商、工具列表、工作目录、权限策略、重试策略和 prompt 细节。服务层把模型调用封装成稳定接口，对上提供统一的 Agent Query / Report Generation API，对下适配 Anthropic SDK、LangChain、文件系统、模板服务和业务工具。

它主要解决四个问题：

1. 能力封装  
   把读取文件、抽取字段、生成报告、渲染模板等动作封装成工具，Agent 只通过受控工具执行业务动作。

2. 权限控制  
   限制 Agent 能访问的目录和工具集合，防止模型执行越权操作。比如只允许读取上传材料目录，只开放必要的 Read/Grep/Report 工具。

3. 流式响应  
   Agent 执行复杂任务可能耗时较长，服务层用流式响应返回中间状态、工具调用和最终结果，前端可以实时展示。

4. 可替换性  
   将 Anthropic、Bedrock、Vertex AI 或其他模型接口屏蔽在服务层之后，后续可以做模型切换、灰度、负载均衡和降级。

可以补一句工程亮点：

> 我更关注的不是“调通一个模型 API”，而是把模型能力接入成一个可控、可扩展、可观测的业务服务。


## 6. Prompt Engineering

这个项目里的 Prompt Engineering 不只是“写一段提示词”，而是围绕结构化抽取任务设计的一套约束机制。

核心策略：

1. 角色约束  
   让模型以银行信贷分析师身份工作，理解授信、贷后检查、五级分类、担保方式、财务指标等业务语义。

2. 任务拆解  
   将任务拆为文件理解、字段定位、证据选择、结构化抽取、缺失判断、字段校验，而不是让模型直接写最终报告。

3. Schema 约束  
   输出不是自然语言，而是固定字段的 JSON/schema。每个字段有名称、说明、类型、格式要求和必填规则。

4. 禁止猜测  
   明确要求模型对没有证据的字段输出“未提供”或“待补充”，而不是补常识或编造。

5. 单位和格式规范  
   金额统一为万元，日期统一为 YYYY年MM月DD日，百分比保留两位，布尔字段统一为是/否。

6. 来源优先级  
   比如营业执照优先用于企业基础信息，财报优先用于财务指标，征信报告优先用于信用状态，合同和批复文件优先用于授信信息。

7. Few-shot 示例  
   给模型少量“字段-证据-输出”的例子，让它学会如何处理缺失、冲突和单位转换。

8. 自检步骤  
   输出前要求模型检查必填字段、数值单位、日期格式、字段是否有证据来源。

面试时可以说：

> 我们不是依赖模型一次性理解所有材料，而是通过 Prompt、schema、检索上下文和后置校验一起收窄模型输出空间。

Q：怎么测试提示词效果

> 我们主要做字段级别的`prompt evaluation`，而不是人工看几次模型输出。具体做法是准备一批代表性授信材料样本，把每个字段的人工标准答案标出来，然后用同一批样本去跑不同版本的 prompt。
>
> 评测指标包括五类：第一是字段准确率，模型抽取值和人工标注是否一致；第二是缺失字段处理准确率，材料中没有的字段是否能正确输出“未提供”；第三是幻觉率，即模型在没有证据时是否编造字段；第四是结构化输出成功率，JSON/schema 是否能被解析；第五是证据绑定率，字段是否带有对应 evidenceRefs。
>
> 每次改 prompt 后，我们会在同一批测试集上做回归测试，观察这些指标有没有提升，而不是只看单个 case。


我们会把测试集分成几类

```
1. 正常字段样本：材料里有明确字段，模型应该正确抽取
2. 缺失字段样本：材料里没有字段，模型应该输出“未提供”
3. 冲突字段样本：多个文档给出不同值，模型应该标记 needs_review
4. 格式敏感样本：金额、日期、百分比、统一社会信用代码
5. 噪声样本：OCR 错误、表格错位、无关上下文很多
```

!!! example "说一个实际的例子"
**调整对象：无证据时保证模型不会臆造数据**

核心不是**简单加一句“不要猜”**，而是把“无证据时怎么做”写成明确规则 + 输出 schema + 反例约束 + 自检要求。

```
你是银行授信材料字段抽取助手。

任务：
请只根据 <evidence> 中提供的证据抽取字段，不得使用常识、经验或推测补全字段。

字段：
creditBalance，含义为“当前授信余额/贷款余额/敞口余额”。

抽取规则：
1. 只有当证据中明确出现授信余额、贷款余额、敞口余额等同义字段，并且能确定金额时，才能填写 value。
2. 如果证据中没有出现该字段，必须输出 value = "未提供"。
3. 如果证据只说明企业名称、注册资本、经营范围等信息，不能推测授信余额。
4. 如果多个证据给出不同金额，保留候选值，并设置 needsReview = true。
5. 每个非“未提供”的字段必须绑定 evidenceRefs。
6. 没有 evidenceRefs 的字段不得自动填写。

输出 JSON：
{
  "fieldName": "creditBalance",
  "value": "...",
  "evidenceRefs": [],
  "confidence": 0-1,
  "needsReview": true/false,
  "reason": "简要说明为什么这样输出"
}

反例：
如果证据中只出现“注册资本 5000 万元”，不能输出“授信余额 5000 万元”。
如果证据中没有授信余额，不能输出“0万元”。
正确输出应为：
{
  "fieldName": "creditBalance",
  "value": "未提供",
  "evidenceRefs": [],
  "confidence": 0,
  "needsReview": true,
  "reason": "给定证据中没有明确授信余额或贷款余额信息"
}
```
</aside>
- 把简单的自然语言指令变成 **可执行的规则**，要说明具体的动作

<aside class="admonition example">
弱提示是：

```
不要猜测。
```

强提示是：

```
如果证据中没有明确出现字段，value 必须等于“未提供”，confidence 必须为 0，needsReview 必须为 true，evidenceRefs 必须为空。
```

模型更容易执行后者，因为它不是抽象原则，而是具体输出动作。
</aside>
- 用`schema`限制模型自由发挥的空间

<aside class="admonition example">
如果让模型自由回答，它可能解释很多：

```
根据企业规模推测，其授信余额可能较高……
```

但如果要求固定 JSON：

```json
{
  "value": "未提供",
  "evidenceRefs": [],
  "needsReview": true
}
```

模型就更不容易展开编造。
</aside>
- 用反例告诉模型什么是错误行为

<aside class="admonition example">
比如明确写：

```
注册资本 5000 万元不能等同于授信余额 5000 万元。
没有看到贷款余额不能推断为 0 万元。
```

这对你们项目特别有用，因为金融字段之间很容易混淆：

```
注册资本 ≠ 授信额度
授信总额 ≠ 授信余额
合同金额 ≠ 贷款余额
销售收入 ≠ 现金流
```
</aside>
- 要求 evidenceRefs 作为入表前提
  - **这是最关键的工程约束**：*没有证据引用，就不能自动填字段*

## 7. LangChain在项目中的作用


![langchain流程编排](/my-blog/2026/05/25/interview/creditagent/image-3.png)

如果面试官追问 LangChain，可以这样讲：

> LangChain 在这个项目里主要承担**链路编排**和 **RAG 工程化角色**，而**不是替代模型本身**。它帮助我们把文档加载、文本切分、embedding、retriever、prompt template、output parser、retry parser 和 evaluation callback 这些步骤串成可维护的链路。

可以展开

1. Document Loader  
   接入 PDF、Word、Excel、OCR 文本，把不同格式统一成 Document 对象，并带上 source、page、section、table、cell 等 metadata。

2. Text Splitter  
   不按固定长度粗暴切，而是结合标题、表格、页码和字段语义切分，避免把一个财务指标或一个表格行切断。

3. Retriever  
   使用混合检索：关键词/BM25 适合找固定字段名，向量检索适合找语义相近内容，业务索引树用于保留层级上下文。

4. Prompt Template  
   不同字段、不同文档类型使用不同模板，避免一个大 prompt 处理所有情况。

5. Output Parser  
   把模型输出解析为结构化字段，并做格式校验。解析失败时触发 retry parser，让模型按错误信息重试。

6. Chain / Runnable 编排  
   把“检索证据 -> 抽取字段 -> 校验 -> 置信度判断 -> 生成澄清问题”串成可复用链路。

7. Evaluation  
   对字段级准确率、必填字段召回率、人工修正率、模型延迟和成本做评估。

一句话：

> LangChain 解决的是 LLM 应用的工程化编排问题，Anthropic 模型解决的是语言理解和结构化推理问题，两者角色不同。

## 8. 文件索引树+字段树机制

```
文件索引树 / 字段树 / evidenceRef
主要存在：PostgreSQL / MySQL / MongoDB 等业务数据库

chunk embedding
主要存在：Milvus / Pinecone / pgvector / Elasticsearch vector 等向量检索系统

原始文件
存在：对象存储，如 S3 / OSS / MinIO
```

### 8.1 为什么需要这套索引

普遍RAG常见问题

1. 扁平`chunk`检索丢失上下文
    一个字段可能在表格里，单独`chunk`只能看到一个数值，看不到它属于哪个年份、哪个科目、哪个客户

> 扁平也就是说：每个`chunk`之间没有层级关系、业务归属关系、字段关系和上下文关系

!!! example "扁平检索"
假设有一张财务报表

```
客户：XX科技有限公司
报表年份：2024年

资产负债表
流动资产：3000万元
负债合计：1800万元
资产总额：5000万元
资产负债率：36%
```

如果系统粗暴切`chunk`，可能变成

```
chunk_01：客户：XX科技有限公司；报表年份：2024年；资产负债表

chunk_02：流动资产：3000万元；负债合计：1800万元

chunk_03：资产总额：5000万元；资产负债率：36%
```

问题来了：当模型检索到`chunk_03`时，只看到

```
资产总额：5000万元；资产负债率：36%
```

但是我们不知道:

```
这是哪个企业的？
是哪一年的？
来自哪张表？
是审计报表还是内部报表？
这个 36% 是资产负债率，不是净利率，也不是负债占比预测值。
```

也就是说 **扁平chunk丢失上下文**
</aside>
2. 复杂表单字段容易混淆
    比如授信总额、授信余额、贷款余额、敞口余额语义接近，扁平检索容易拿错

3. 缺乏字段级校验
    普通检索只返回文班，不知道这个文本应该填到哪个字段，也不知道业务格式和业务规则

4. 难以解释来源
    银行场景需要知道字段来自哪份文档、哪一页、哪个表格而不只是给一个答案 

### 8.2 这套索引是什么

这套索引可以理解为表单字段树、文件索引树和一组`evidenceRef`映射关系。

**字段树**

``` text
授信后检查报告
├── 企业基本信息
│   ├── 客户名称
│   ├── 统一社会信用代码
│   ├── 注册资本
│   └── 法人代表
├── 授信信息
│   ├── 批复编号
│   ├── 授信总额
│   ├── 授信余额
│   └── 担保方式
├── 财务分析
│   ├── 资产负债率
│   ├── 流动比率
│   └── 净利率
└── 风险结论
    ├── 主要风险点
    └── 检查结论
```

每个字段节点包含：

- 字段名称
- 字段别名
- 字段说明
- 数据类型
- 格式规范
- 必填规则
- 推荐来源文档
- 校验规则
- 置信度阈值

**文件索引树**

```text
客户材料包
├── 营业执照.pdf
│   ├── 第1页
│   │   ├── 基础登记信息区域
│   │   └── 经营范围区域
├── 2024财务报表.xlsx
│   ├── 资产负债表
│   │   ├── 流动资产
│   │   └── 负债合计
│   └── 利润表
├── 企业征信报告.pdf
│   ├── 信贷记录
│   └── 不良记录
└── 授信批复.docx
    ├── 授信方案
    └── 担保条件
```

每个证据节点包含：

- 文档名
- 页码/表名/章节
- 文本内容
- 表格坐标
- OCR 坐标
- 文档类型
- embedding
- 关键词索引
- 可信来源等级

两棵树之间建立映射

```text
字段节点: 授信信息/授信余额
候选证据:
1. 授信批复.docx / 授信方案 / 第2段
2. 企业征信报告.pdf / 信贷记录 / 第4页
3. 银行流水说明.xlsx / 贷款余额字段
```

![关系图](/my-blog/2026/05/25/interview/creditagent/image-4.png)

```json
{
  "fieldPath": "企业基本信息/注册资本",
  "value": "5000万元",
  "evidenceRefs": [
    {
      "document": "营业执照.pdf",
      "page": 1,
      "matchedText": "注册资本：5000万元"
    },
    {
      "document": "公司章程.docx",
      "section": "第3条",
      "matchedText": "公司注册资本为人民币5000万元"
    }
  ],
  "excludedEvidence": [
    {
      "document": "2024财务报表.xlsx",
      "reason": "资产总额不是注册资本"
    }
  ],
  "confidence": 0.96,
  "needsReview": false
}
```

### 8.3 检索流程

字段填写时走从粗到细检索：

1. 根据字段路径定位字段节点
    - 例如：财务分析/资产负债表
2. 读取字段元数据
    - 包括别名、推荐文档、字段类型、格式要求
3. 先做文档级别过滤
    - 比如企业基础信息有限搜索营业执照、信用状态有限搜索征信报告
4. 再做章节级别/表格级别检索
    - 在相关文档内部找标题、表格、段落
5. 最后做`chunk`级语义检索
    - 使用`embedding + keyword`混合召回
6. 对候选证据排序
    - 综合字段匹配度、来源优先级、事时间新鲜度、文档可信度和模型置信度
7. 后置校验
   - 校验格式、单位、数值范围和跨文档一致性

### 8.4 这套索引的价值

文件索引树和字段树的组合，本质上是把表单结构和文档结构都显式建模，让模型从 *读一堆材料生成答案*变成 *围绕某个字段在索引树里面找证据*。它减少了上下文噪音，也rag每个字段可解释、可校验、可回溯

## 9. 交互式复核/填写流程

### 9.1 为什么需要交互式复核

银行表单不能完全依赖模型自动填，因为：

1. 有些材料缺失，模型不能猜
2. 不同文档可能冲突，例如营业执照和内部系统中的注册地址不一致。
3. 部分字段属于高风险字段，例如授信余额、五级分类、担保方式、征信不良记录。
4. 银行需要审计链路，知道谁确认了什么信息。

### 9.2 字段状态机

可以把每一个字段看成一个状态机：

```text
未填写
  -> 自动候选
  -> 已校验
  -> 待用户确认
  -> 用户已确认
  -> 已填充模板
```

异常状态：

```text
证据不足
字段冲突
格式错误
需要补充材料
人工覆盖
```

### 9.3 触发人工交互的条件

1. 置信度低于阈值  
   比如模型只给 0.72，但字段要求 0.9 以上。

2. 多个候选值冲突  
   例如授信余额在征信报告和内部批复中不一致。

3. 必填字段缺失  
   系统提示用户上传对应材料或手动补充。

4. 高风险字段  
   即使置信度高，也要求人工确认。

5. 校验不通过  
   如金额单位异常、日期格式错误、统一社会信用代码位数不对。


<aside class="admonition example">
系统不会问泛泛的问题：

> 请补充客户信息。

而是问具体问题：

> “授信余额”字段存在两个候选值：  
> A. 1,200 万元，来源：授信批复，第 2 页  
> B. 1,150 万元，来源：企业征信报告，第 5 页  
> 请确认本次报告应使用哪个值，或手动输入最新余额。
</aside>
**这类交互的价值**

- 用户只处理模型不确定的部分
- 自动化率高的字段直接填
- 风险字段有人工确认
- 每个字段保留证据和确认记录

### 9.4 面试总结

交互式复核不是降低自动化能力，而是把 LLM 的不确定性显式暴露出来，让系统在准确率、效率和合规之间取得平衡。


## 10. 98%准确率

推荐口径：

> 我们按字段级准确率评估，而不是按整份报告完全一致评估。对于一批标注过的企业材料，每个表单字段都有人工标准答案。模型抽取结果与标准答案比对，普通文本字段用精确匹配或归一化匹配，金额和百分比允许极小格式差异，日期统一格式后比较。最终在核心字段集合上，自动抽取准确率提升到约 98%。

可以补充：

准确率提升来自四个方面：

1. Prompt 和 schema 约束  
   减少输出格式错误和字段遗漏。

2. 文件索引树和字段树  
   减少无关上下文干扰，提高字段证据召回率。

3. 校验规则  
   对日期、金额、统一社会信用代码、百分比、财务指标做后置校验。

4. 交互式确认  
   对低置信度字段不盲填，通过人工确认减少最终报告错误。

如果被追问“98% 是自动化前还是人工确认后”，建议区分：

> 自动抽取阶段我们关注字段候选准确率；进入交互式确认后，最终入表准确率会更高。简历里的 98% 指的是核心字段在优化后自动提取结果相对人工标注的字段级准确率。

我们的 98% 不是让模型自己打分，也不是看整篇报告像不像，而是做字段级准确率评测。

具体方法是先准备一批人工标注过的授信材料样本，每份样本包含原始材料、目标字段、标准答案和对应证据来源。模型抽取后，我们先做归一化处理，比如*金额统一到万元、日期统一格式、公司名称去空格和标点、百分比统一精度*，然后逐字段和人工标准答案比对。

对普通文本字段，用精确匹配或归一化匹配；对金额、日期、百分比这种格式敏感字段，用*规则归一化后*比较；对材料中确实缺失的字段，**如果模型输出“未提供/待补充”，也算正确**。最后按核心字段集合统计正确字段数除以总字段数，得到字段级准确率。

平台方面，开发和调 prompt 阶段可以用 LangSmith 做 dataset、experiment 和 trace 管理，也可以用 Ragas 看 RAG 链路的 context recall、faithfulness 等指标；如果只是对比 Claude prompt 版本，也可以用 Anthropic Console 做测试样例和输出对比。但最终 98% 的业务指标还是以人工标注集上的字段级准确率为准。

```
人工标注样本集
   ↓
运行抽取链路
   ↓
字段结果归一化
   ↓
逐字段比对标准答案
   ↓
统计准确率、召回率、幻觉率、证据绑定率
   ↓
分析 bad cases
   ↓
调整 prompt / schema / retriever / 校验规则
   ↓
回归测试
```

1. 检索层
   看正确证据有没有被召回。
   指标：context recall、top-k 命中率。

2. 抽取层
   看模型从正确证据中抽出的字段值是否正确。
   指标：字段级准确率、字段召回率。

3. 结构化输出层
   看 JSON/schema 是否稳定。
   指标：JSON 解析成功率、schema validation pass rate。

4. 证据绑定层
   看字段是否有 evidenceRefs。
   指标：证据绑定率、无证据字段幻觉率。

5. 最终入表层
   看经过校验和人工复核后的字段是否可用于报告。
   指标：最终字段正确率、人工修正率。


## 11. 熔断、降级、负载均衡怎么讲

### 11.1 为什么LLM系统需要这些策略

LLM 调用和普通 RPC （Remote Procedure Call，远程过程调用）不同：

- 延迟高
- token 成本高
- 容易受限流影响
- 第三方服务可能波动
- 输入大小会影响响应时间
- 同一任务可能需要多轮调用

银行业务不能因为模型接口波动就卡死，所以要在模型网关层做稳定性设计。

### 11.2 熔断

熔断器有三个状态：

1. Closed  
   请求正常，正常调用模型。

2. Open  
   - 熔断打开，暂时不调用这个熔断器保护的服务
   - 当错误率、超时率或 P95 延迟超过阈值时，暂时停止调用该模型。
   - 意义：不要继续把请求打到一个已经明显不稳定的服务上，否则会拖垮整个系统

3. Half-open  
    - 过了一段时间后，不确定服务恢复没有，所以先**放少量请求过去试试**
    - 过一段时间后放少量请求试探，如果成功恢复到 Closed，否则继续 Open。

**核心机制**：请求失败/超时**累计到阈值后**，熔断器先进入 Open；Open 会**持续一段冷却时间**；冷却时间结束后，系统**不会立刻完全恢复**，而是进入 Half-open，只放少量请求去试探

```
Closed 正常调用
   ↓ 失败太多 / 超时太多 / 延迟太高
Open 暂停调用
   ↓ 等待一段恢复时间
Half-open 少量试探
   ↓ 试探成功
Closed 恢复正常

Half-open 少量试探
   ↓ 试探失败
Open 继续熔断
```

![熔断机制示意图](/my-blog/2026/05/25/interview/creditagent/image-5.png)

触发条件示例：

- 1 分钟内错误率超过 30%
- 连续 5 次超时
- P95 延迟超过 20 秒
- 供应商返回限流错误

### 11.3 降级

降级不是简单报错，而是保留核心流程：

1. 模型降级
    主模型不可用时切换到备用供应商或轻量模型
2. 能力降级
    复杂综合分析不可用，先完成基础字段抽取
3. 规则降级  
   对统一社会信用代码、日期、金额等字段使用规则/OCR/正则提取。

4. 缓存降级  
   对已处理过的材料复用历史抽取结果。

5. 人工流程降级  
   系统生成待补充字段清单，让用户手动填关键字段。 

### 11.4 负载均衡

**如何理解负载均衡的含义**

> 当系统有多个模型服务/多个接口可以调用时，不要所有请求都打到一个地方，而是根据规则把请求分配到不同模型、不同供应商、不同区域或者不同的endpoint上，让系统更稳定、更快、更省钱

模型负载均衡可以按照：

- 供应商：Anthropic direct / AWS Bedrock / Google Vertex
- 区域：新加坡或其他合规区域
  - 区域级负载均衡不是只为了快，还涉及数据合规。金融客户材料不能随意跨区域，所以模型网关需要根据租户、任务和数据等级选择合规区域内的 endpoint。
- 模型能力：Sonnet 处理主任务，Haiku 处理轻量字段抽取
- 延迟：选择当前响应最快的 endpoint
- 配额：根据剩余额度和限流情况分配请求

常见策略：

- weighted round-robin:加权轮询，能力强的多分一些，能力弱的少分一点(权重根据稳定性、成本、速度、配额、模型能力、供应商优先级来设置)
- least latency：哪个 endpoint 最近响应最快，就优先发给谁
- token bucket 限流
- exponential backoff with jitter（指数退避 + 随机抖动）：  
  - 指数退避：等待时间指数增加
  - 抖动：不要所有请求都等1、2、4、8秒，在这个基础上加一点随机事件，如果很多请求同时失败，又同时在 2 秒后重试，会再次把服务打爆
- idempotency key（幂等键） 防止重复生成报告
  - 比如如果点击生成报告时网络原因导致卡了需要再点一次，同一个任务不能由于前端任务重复生成多个相同的报告
  - 后端代码负责接收、生成、校验和使用 idempotency key；数据库或 Redis 负责持久化记录这个 key 对应的处理状态和结果，防止重复执行。

## 12. 面试高频追问与回答

### Q1：你说主导 Agent SDK 服务层，具体主导了什么？

回答：

> 我主要负责把 Agent 能力服务化。包括接口定义、模型配置抽象、工具注册机制、流式响应协议、工作目录和工具权限控制、业务工具封装、错误处理和日志观测。我的目标是让上层业务不用关心底层模型 SDK，只需要调用统一的 Agent 服务。

### Q2：文件索引树和普通向量数据库有什么区别？

回答：

> 普通向量检索通常是扁平 chunk 召回，适合问答，但对复杂表单填写不够。文件索引树显式建模了任务、业务分类、文档和 chunk，字段树显式建模了报告字段和校验规则，两者结合后可以按业务域和字段路径做检索，并保留字段规则和证据来源。它不是替代向量检索，而是在向量检索上增加业务结构和可解释性。

### Q3：怎么防止模型幻觉？

回答：

> 我主要通过四层控制：第一，Prompt 要求没有证据就输出未提供；第二，检索阶段只提供相关证据，减少模型发散；第三，schema 输出限制字段类型和格式；第四，后置校验要求字段必须绑定来源，高风险或低置信度字段进入人工确认。

### Q4：准确率 98% 怎么评估？

回答：

> 我们按字段级准确率评估。先准备人工标注的标准答案集，对核心字段做归一化比对，比如金额统一单位、日期统一格式、百分比统一精度。模型输出和标准答案一致就算正确。对于缺失字段，如果材料中确实没有，模型输出未提供也算正确。98% 指核心字段集合上的字段级准确率。

### Q5：如果模型返回 JSON 格式错了怎么办？

回答：

> 生产链路里会有 output parser 和 schema validator。解析失败会把错误信息反馈给模型重试；多次失败会降级到字段级抽取或人工确认。不会让格式错误的结果直接进入模板。

### Q6：为什么用交互式复核，不是全部自动填？

回答：

> 银行场景不能只追求自动化率，还要保证准确性和合规。交互式复核只处理模型不确定或业务高风险的字段，大部分高置信度字段仍然自动填。这样既节省人工，又保留关键字段的人为确认和审计链路。

### Q7：如果两个文档给出的注册资本不一致怎么办？

回答：

> 系统先根据来源优先级和时间新鲜度排序。比如企业基础信息优先以最新营业执照或工商信息为准。如果冲突无法自动解决，就把两个候选值、来源文档、页码和抽取时间展示给用户确认，并记录人工选择。

### Q8：LangChain 具体带来了什么价值？

回答：

> 它把文档加载、切分、检索、prompt template、模型调用、output parser 和重试机制标准化了。没有 LangChain 也可以写，但链路会比较分散，不利于复用、监控和评估。我们用它来做 RAG 和字段抽取链路编排。

### Q9：为什么不用传统 OCR + 规则就够了？

回答：

> 规则适合固定格式字段，例如统一社会信用代码、日期、金额。但银行材料格式差异大，很多字段需要理解上下文，比如经营情况变化、风险缓释措施、主营业务分析、贷款用途落实情况。LLM 更适合处理这类半结构化和语义型字段。实际系统里规则和 LLM 是结合使用的。

### Q10：如何降低成本？

回答：

> 首先通过文件索引树和字段树减少上下文长度，不把全量文档发给模型；其次做字段分级，简单字段用小模型或规则抽取，复杂字段才用强模型；第三对文档解析和字段结果做缓存；第四批量任务做异步队列和限流，避免重复调用。

### Q11：Agent 和普通 RAG 问答有什么区别？

回答：

> 普通 RAG 更像问答系统，输入问题，输出答案。Agent 在这个项目里是业务流程执行者，它不仅回答，还能调用工具读取文件、抽取字段、校验结果、生成报告、触发澄清问题。它有任务状态和工具编排能力。

### Q12：模型服务挂了怎么办？

回答：

> 模型网关会先重试，如果错误率持续升高就触发熔断。之后请求会切到备用模型或备用 endpoint；如果仍不可用，就降级为规则抽取、历史缓存、部分报告生成或人工补录，不让业务流程完全中断。

### Q13：如何处理 Prompt Injection？

回答：

> 文档内容只作为数据，不作为系统指令。系统 prompt 和工具权限由服务端控制，用户上传文档不能改变 allowed tools 或工作目录。对工具调用参数做服务端校验，模型不能直接执行未授权动作。

### Q14：如果让你继续优化这个项目，你会做什么？

回答：

> 我会优先补三块：第一，完善文档解析能力，尤其是 OCR 和表格结构解析；第二，做字段级评测集和自动化评估，持续跟踪准确率、召回率和人工修正率；第三，补生产级模型网关，包括限流、熔断、降级、审计日志和多模型路由。

## 13. STAR 故事

### Situation

银行贷后检查和客户资料收集依赖大量人工录入，材料格式复杂，客户经理需要从多份文档里找字段、填表、写报告，耗时且容易出错。

### Task

我要负责设计 Agent 服务层和核心自动化链路，让系统能够自动读取客户材料、抽取结构化字段、校验字段可信度，并生成标准授信后检查报告。

### Action

我做了四件事：

1. 把模型能力封装成 Agent 服务层，对外提供统一接口，对内适配 Anthropic SDK、LangChain、文件系统和模板服务。
2. 设计结构化抽取 prompt 和 schema，要求模型按字段输出，并对缺失值、单位、日期格式和来源优先级做约束。
3. 设计文件索引树和字段树，把授信材料组织成业务语义和 chunk 级证据，把报告模板拆成可校验字段，字段填写时按业务分类和字段路径精准检索证据。
4. 引入交互式复核和稳定性策略，对低置信度字段人工确认，对模型调用做熔断、降级和负载均衡。

### Result

最终系统能自动完成客户材料解析、字段抽取、表单填写和 Word 报告生成。相比原来手工录入，核心字段抽取准确率提升到约 98%，复杂表单填写更稳定，且每个字段都有来源证据和确认记录，满足银行业务对准确性和可追溯性的要求。

## 14. Workflow

面试官问“你这个项目里的 workflow 是什么”，可以这样回答：

> 这个项目里的 workflow 指的是把原本复杂、非结构化的授信材料处理过程拆成一条明确的业务流水线，而不是把所有文件一次性丢给模型自由生成结果。它包括任务创建、文件预处理、真实内容解析、文件索引树构建、结构化字段抽取、多来源融合、报告生成、人工复核和 Agent 辅助分析。

为什么不用模型一步到位生成报告：

> 一步到位实现简单，但可控性差。结果出错时很难判断是文件解析错、字段抽取错、融合逻辑错，还是报告组织错。拆成 workflow 后，每一步都有明确输入输出，可以单独优化、重试、监控和追溯。

阶段拆分可以按四层讲：

1. 输入处理  
   任务创建、文件上传、命名规范、元数据登记、去重、清洗、标准化。

2. 知识构建  
   图片、PDF、Excel、音频进入各自解析器，解析结果再组织成文件索引树和 chunk 级知识单元。

3. 结果生成  
   在索引树上做结构化抽取、多来源融合、冲突处理、置信度评分和报告生成。

4. 人工协同  
   对低置信度、高风险或冲突字段做人工复核，并让 Agent 支持证据查询、章节重生成和完整性检查。

Workflow 和 Agent 的关系：

> workflow 负责主流程，强调稳定、可追溯和可复现；Agent 负责辅助分析，强调灵活交互。两者共享同一套索引树和证据底座，但职责不同。正式报告生成不能完全交给开放式 Agent，否则路径不稳定、审计困难。

## 15. 置信度算法

算法分四步：

1. 生成字段候选  
   从每个 chunk 中抽取字段候选。比如 `registeredCapital` 可能来自营业执照、征信报告和公司章程。

2. 计算候选基础分  
   可以用：

```text
candidateScore =
  w1 * parseScore +
  w2 * locateScore +
  w3 * sourceScore +
  w4 * schemaScore +
  w5 * ruleScore
```

各项含义：

- `parseScore`：解析质量，例如 OCR 置信度、图像质量、PDF/Excel 解析可靠性。
- `locateScore`：定位可靠性，例如是否来自标准 key-value 区域、表格单元格或正文推断。
- `sourceScore`：来源权重，例如营业执照、征信报告、财务报表、合同、自述材料权重不同。
- `schemaScore`：字段匹配程度，例如正则/key-value 强匹配高于自然语言总结。
- `ruleScore`：规则校验结果，例如日期、金额、信用代码、百分比是否合法。

3. 多候选聚合  
   先把 `5000万元`、`5000 万`、`RMB 5000万元` 归一化到同一个值组，再计算组分：

```text
groupScore(v) =
  alpha * maxCandidateScore(v) +
  beta * avgCandidateScore(v) +
  gamma * supportBonus(v)
```

`supportBonus` 用于奖励多独立来源一致，但要设置上限，不能无限加分。

4. 冲突惩罚  
   如果存在其他冲突值，即使最终选择了最高分候选，也要下调置信度：

```text
finalConfidence = selectedGroupScore * (1 - conflictPenalty)
```

比如注册资本字段，营业执照和公司章程都支持 `5000万元`，但征信报告出现 `3000万元`，系统可以仍建议 `5000万元`，同时把字段状态标记为 `needs_review`。

最终决策可以分三档：

1. 高置信度  
   自动填模板，正常进入后续流程。

2. 中置信度  
   可填模板，但界面标记“建议复核”，保留 evidenceRefs。

3. 低置信度  
   不自动定稿，进入人工复核或填“待补充”。

如果被问“权重怎么定”，可以这样答：

> 前期会用可解释的规则权重快速上线，比如来源权重、字段模式权重和规则校验权重由业务经验设定。等系统积累了人工复核数据和标注样本后，再把字段最终是否正确作为监督信号，用逻辑回归或树模型学习更合理的加权方式，并做 calibration。也就是先规则化、可解释地落地，再逐步演进为数据驱动的置信度模型。
